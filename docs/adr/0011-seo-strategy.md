# ADR-0011: SEO Strategy — Static Site Generation for SPA
## Status: Accepted
## Date: 2026-03-21
## Decider: Chris Novak (CTO)

---

## Context

The platform has a fundamental SEO tension: the owner specified a pure React SPA (not Next.js with SSR), but many pages must be indexed by search engines for the platform to fulfil its public mission:

- **Court decisions** — judges, lawyers, and the public search for specific decisions by keyword. These must rank in Google.
- **Expert witness profiles** — legal professionals need to find experts by name and speciality.
- **News posts** — announcements from the Croatian judicial community should be indexed.
- **Static pages** — About, Contact, Free Legal Aid.

A pure SPA returns nearly empty HTML on the first request (just `<div id="root"></div>`). Googlebot can execute JavaScript, but indexing quality for SPAs is lower and slower than for server-rendered HTML. The current site, despite being ancient, is indexed because it serves HTML directly.

The 301 redirect map (old `.aspx` URLs → new clean URLs) must not lose existing search ranking for the case law database.

---

## Decision

**`vite-plugin-ssg`** for static HTML generation at build time, combined with **`react-helmet-async`** for dynamic `<head>` management.

At build time, `vite-plugin-ssg` crawls all known routes and generates static HTML files for each. The Nginx `web` service serves these static HTML files. When Googlebot requests `/hr/sudska-praksa/123-naziv-odluke`, it receives pre-rendered HTML with the decision title, meta description, and structured data — no JavaScript execution needed.

Dynamic route pre-rendering: during the SSG build step, a script fetches all court decisions, expert profiles, courts, and news posts from the Payload CMS API and generates the full route list. All known entities are pre-rendered.

**What is NOT pre-rendered:**
- Search results pages (dynamic, query-dependent)
- User authentication pages (login, register, member area)
- Bankruptcy listings (changes frequently — these use React Query for client-side fetching)

**Sitemap:** Generated as a build step by `scripts/generate-sitemap.ts` which calls Payload's API, collects all public URLs, and writes `web/public/sitemap.xml`. This file is served statically by Nginx.

**`hreflang`:** Every pre-rendered page includes `<link rel="alternate" hreflang="hr">` and `<link rel="alternate" hreflang="en">` pointing to both language versions. For pages with no English translation, only `hreflang="hr"` is included.

**Structured data (JSON-LD):**
- Homepage: `LegalOrganization`
- Court decision detail: `LegalCase` (schema.org)
- Expert witness profile: `Person` + `OccupationalExpert`
- Court detail: `Courthouse`
- News post: `NewsArticle`
- Breadcrumbs: `BreadcrumbList` on all nested pages

**301 redirects:** Old `.aspx` URL patterns (e.g., `/vjestaci.aspx?id=123`) are redirected via Nginx rewrite rules generated by `scripts/migrate/generate-redirects.ts`. This preserves existing Google rankings for the case law database — critical for organic traffic.

---

## Alternatives Considered

**Next.js 15 with App Router SSR/SSG (would have solved this automatically)**
- If Next.js had been chosen, this entire ADR would be unnecessary — SSG is built in
- This is a trade-off of the owner's React + Vite decision
- Accept it and solve it with `vite-plugin-ssg`

**Puppeteer/Rendertron prerendering service**
- A headless Chrome prerendering service that intercepts crawler requests and serves pre-rendered HTML
- Pros: Works with any SPA without code changes
- Cons: An entire additional service to maintain; adds latency; complex Nginx routing to distinguish crawlers from users; operationally fragile
- Rejected: `vite-plugin-ssg` is cleaner and generates the HTML at build time, not request time

**Dynamic rendering (serve SSR to bots, SPA to humans)**
- Different response based on `User-Agent`
- Pros: No build-time step needed
- Cons: Google officially discourages cloaking (serving different content to bots vs humans); maintenance overhead of two rendering paths
- Rejected: Against Google's guidelines

**Accept poor SEO for the SPA**
- Simply accept that Googlebot's JavaScript rendering will eventually index the site
- Rejected: Case law decisions and expert profiles are the core value of this platform. If they don't appear in search results, the site fails its public mission.

---

## Consequences

**Positive:**
- Court decisions and expert profiles are fully indexed from day one
- `vite-plugin-ssg` generates static HTML that can be served by Nginx with zero server-side processing — excellent performance
- The pre-rendered HTML includes full structured data for rich snippets in Google search results
- Rebuild webhook from Payload (when content is published) triggers a GitHub Actions rebuild — new content is indexed within minutes

**Negative:**
- SSG build takes longer as the content corpus grows (thousands of court decisions × API calls)
  - Mitigation: Cache the API responses during the SSG build; use incremental builds where possible
- When a new court decision is added via Payload admin, the site must be rebuilt to generate its static HTML
  - Mitigation: Payload webhook → GitHub Actions → Docker build → deploy. Estimated rebuild time: 5-10 minutes for a full corpus.
- Route list must be maintained — new collections must be added to the SSG crawler configuration

**Risk:**
- `vite-plugin-ssg` is a community plugin (not an official Vite project). If it becomes unmaintained, migration to another SSG solution is required. This is a known risk; it is the best available option for this stack. Monitor for updates; pin the version.
