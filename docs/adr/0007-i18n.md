# ADR-0007: Internationalisation — react-i18next
## Status: Accepted
## Date: 2026-03-21
## Decider: Chris Novak (CTO)

---

## Context

The platform is bilingual: Croatian (primary, ~95% of users) and English (international users, partner institutions, foreign legal professionals). The current site handles language switching via a URL query parameter (`?Lng=hr`). The new site must:
- Use clean URL paths for language: `/hr/...` and `/en/...`
- Allow search engines to index both language versions separately (with `hreflang` tags)
- Fall back to Croatian when English translations are missing (most content is Croatian-only)
- Support translation of UI strings (navigation, labels, errors, buttons)
- Be extendable to a third language (Serbian, North Macedonian) without architectural changes

The owner specified react-i18next.

---

## Decision

**react-i18next 15** with **i18next 24** for internationalisation.

Language routing: React Router 7 handles `/hr/` and `/en/` path prefixes. The root `/` redirects to `/hr/` (default language). Language detection order:
1. URL path prefix (highest priority)
2. `localStorage` (persisted user preference)
3. Browser `Accept-Language` header
4. Fallback: `hr`

Translation files are split by namespace and lazy-loaded:
- `common` — shared UI strings (buttons, labels, errors, dates, pagination)
- `nav` — navigation labels
- `home` — homepage copy
- `decisions`, `experts`, `courts`, `bankruptcy`, `calculator`, `news`, `contact`, `auth` — feature-specific

Payload CMS content (court decisions, news posts, expert profiles) has a `lang` field (`hr` | `en`). The frontend filters by `?where[lang][equals]=hr` based on the current language. Where English content doesn't exist, Croatian content is shown with a "Translation not available" notice.

`hreflang` links are injected per page via `react-helmet-async`:
```html
<link rel="alternate" hreflang="hr" href="https://sudacka-mreza.hr/hr/sudska-praksa/123" />
<link rel="alternate" hreflang="en" href="https://sudacka-mreza.hr/en/court-decisions/123" />
<link rel="alternate" hreflang="x-default" href="https://sudacka-mreza.hr/hr/sudska-praksa/123" />
```

---

## Alternatives Considered

**next-intl**
- Referenced in the earlier PROJECT_PLAN.md
- Pros: Excellent SSR integration with Next.js; built-in URL routing
- Cons: Designed for Next.js App Router; using it with React + Vite requires a custom adapter that essentially rebuilds what react-i18next already provides
- Rejected: Owner chose React + Vite, not Next.js; react-i18next is the correct tool for this stack

**FormatJS / react-intl**
- Pros: ICU message format support; good for complex pluralisation
- Cons: More complex API; Croatian pluralisation rules are moderately complex but not extreme; react-i18next handles them adequately with `_plural` key suffix; smaller community than react-i18next
- Rejected: Unnecessary complexity for this use case

**Custom i18n solution**
- Simple JSON key lookup with a React context
- Pros: No dependency
- Cons: Reinventing pluralisation, interpolation, lazy loading, namespace separation, language detection
- Rejected: react-i18next solves all of these correctly

---

## Consequences

**Positive:**
- react-i18next is the most widely used React i18n library — easy to find help and Croatian developers familiar with it
- Namespace lazy loading keeps the initial bundle small
- Language switching is instant (client-side, no page reload)
- Falls back gracefully when English translations are missing

**Negative:**
- Translation files must be maintained in two languages. For MVP, the English translations will be incomplete — this is acceptable and expected
- URL structure doubles all routes (`/hr/sudska-praksa/...` and `/en/court-decisions/...`) — this requires careful React Router 7 route definition with a language prefix wrapper route

**Risk:**
- Croatian slugs in URLs (e.g., `/hr/sudacka-praksa/`) contain Croatian characters that must be percent-encoded in HTTP but look correct in browser address bars. The `slugify.ts` utility MUST convert `č→c`, `š→s`, `ž→z`, `ć→c`, `đ→d` for URL slugs to avoid encoding issues in emails and shared links. However, human-readable URLs displayed in the browser should use the original Croatian characters where possible.
- The Payload CMS admin UI uses its own separate localisation system (defined in `payload.config.ts`) and is independent of react-i18next. Croatian admin UI strings must be added separately.
